# 全模块缺陷与优化分析

> 审查日期：2026-10-18
> 审查范围：`toolbox.py`、`config.py`、`main.py`、`settings_page.py`、`common/`（11 个文件）、`plugins/`（9 个插件）、`toolbox.spec`、`build.py`、`verify_packaging.py`、`test/` 与 CI 配置

## 一、总体结论

项目整体架构清晰，共享组件层（`common/app_settings.py` 的原子写 + `.bak` 备份、`i18n.py` 的弱引用绑定、`empty_folder_cleaner.py` 的安全删除设计）实现严谨。但存在若干**高优先级缺陷**，集中在三类：

1. **数据安全**：文件去重插件存在越界扫描与误删风险，格式转换存在静默覆盖源文件。
2. **崩溃 / 假死**：Worker 线程信号遮蔽、删除操作占用 UI 线程、画布内存无上限。
3. **规则落空**：多处名为"保护"的实现（`check_file_writable`、主题适配选择器、样式表 `f` 前缀）实际失效，形成误导性死代码。

以下按严重程度分级。**高**为数据丢失、崩溃、功能失效；**中**为体验、性能、语义错误；**低**为规范与可维护性。

## 二、高严重度问题

### H1. 文件去重：删除操作在主线程执行，UI 冻结且不可取消 ✅

- 位置：`plugins/file_deduplicator.py:871-893`
- 问题：删除循环直接在 UI 线程运行，循环内无事件处理，也无可取消机制。批量删除数千文件时进度条不重绘、窗口无响应。
- 影响：与项目"长操作必须走 QThread"规则冲突；用户误以为程序卡死而强杀进程，导致删除中途中断。
- 修复：参照 `empty_folder_cleaner` 将删除移入 Worker，进度经信号上报，并响应取消标志。

**修复方案（2026-10-18 已实施）：** 新增 `FileDeletionWorker(BaseWorker)`——删除循环移入 Worker.run()，逐文件 `progress.emit(index, total)` 与 `status` 消息，响应 `cancel_requested` 支持取消；UI 侧确认对话框后启动 Worker，删除期间禁用删除/扫描按钮与路径输入，新增 `update_delete_progress()` 与 `delete_finished()` 回调展示成功/失败统计并按勾选状态触发重扫。顺带移除原 UI 循环里无条件的 `os.chmod(S_IWRITE)`（M11 子项）与 `import stat`。

### H2. 文件去重：`os.walk` 跟随 junction / symlink，可能扫描并删除根目录之外的文件 ✅

- 位置：`plugins/file_deduplicator.py:49-63`（扫描）、`:837-839`（删除）
- 问题：`os.path.islink()` 对 Windows junction 返回 `False`，`os.walk` 会进入 junction 指向的外部目录（如经典 `Application Data` 循环链接会死循环）；同时扫描未排除符号链接文件。排序后若链接排在前，保留的是链接，`os.remove` 删掉的却是真实数据文件。
- 影响：**不可逆数据丢失**；全项目风险最高的问题。
- 修复：改用 `os.scandir` + `entry.is_junction()`（`empty_folder_cleaner.py:36-48` 已正确实现，可反哺）；扫描时用 `os.path.islink()` 排除链接文件，保留决策强制选择真实文件。

**修复方案（2026-10-18 已实施）：** 新增模块级安全工具函数 `_is_junction` / `_is_link_like` / `_is_link_path` / `_is_within_root`（与 `empty_folder_cleaner.py:36-61` 同款安全模式）；`_iter_regular_files` 用 `os.scandir` 递归遍历，`entry.is_dir(follow_symlinks=False)` 防止进入 junction，跳过符号链接/junction 文件与 Windows 保留设备名；`run()` 扫描段改用该遍历器，并对每个文件再查 `_is_link_path` 排除链接文件，不纳入去重；删除 Worker 对每个目标复核 `_is_within_root(root, target)`，越界目标拒绝删除并计入失败。

### H3. 格式转换：同目录同格式转换静默覆盖源文件 ✅

- 位置：`plugins/image_format_converter.py:72`
- 问题：`out_path = f"{base}.{ext}"` 未加后缀。`a.jpg` 转 JPEG 且未指定输出目录时，源文件被 quality=85 重压缩后原地覆盖，无任何提示；批量中 `a.png`→JPEG 还会覆盖同目录已存在的 `a.jpg`（可能正是待处理文件，结果依赖处理顺序）。
- 影响：**源文件数据丢失**。
- 修复：与另两插件一致追加后缀（如 `_converted`），或在 save 前比较 `out_path` 与源路径 / 已有文件并跳过提示。

**修复方案（2026-10-18 已实施）：** Worker 记录归一化的源文件路径集合 `_source_paths`；`_convert_one` 中若输出路径 `out_abs` 命中该集合（含自身 `a.jpg`→JPEG、或 `a.png`→JPEG 落在既有 `a.jpg`），则改写为 `{base}_converted.{ext}`，避免就地覆盖源文件/覆盖待处理文件；独立输出目录场景不加后缀（无冲突）。新增回归测试验证冲突时源文件字节不变、输出到 `_converted`。

### H4. `check_file_writable` 以追加模式探测，凭空创建 0 字节文件 ✅

- 位置：`common/utils.py:172`；调用方 `plugins/image_to_pdf.py:113`、`plugins/pdf_merger.py:43`
- 问题：目标文件不存在时 `open(path, 'ab')` 直接创建 0 字节文件。本意是落实 Rule 9（写前检查占用），实际先在用户选择的输出路径留下空文件；若后续处理失败（如全部图片损坏），磁盘上残留 0 字节"成品"误导用户。
- 影响：Rule 9 产生反效果；`image_stitcher.py:243-259` 同源问题。
- 修复：先 `os.path.exists` 判断，不存在时仅验证父目录可写；或探测后删除探针文件。

**修复方案（2026-10-18 已实施）：** `common/utils.py` 的 `check_file_writable` 改为——目标文件已存在时才以追加模式探测占用；目标不存在时不再创建任何文件，改为复用 `check_dir_writable` 仅验证父目录可写（父目录也不存在时直接视为可写，交由最终保存阶段报错）。调用方（`image_to_pdf.py`、`pdf_merger.py` 等）无需改动，语义不变。`image_stitcher.py:243-259` 同源问题确认存在（`open(out_path,'ab')` 会凭空创建 0 字节文件），已改为复用修复后的 `check_file_writable`。测试更新：`test_utils.py` 原 PermissionError 用例适配新语义（目标需先存在才走探测分支），新增"目标不存在不创建探针文件"与"父目录不可写返回错误"两个回归用例。

### H5. `BaseWorker.finished` 信号遮蔽 QThread 内置信号 ✅

- 位置：`common/base_worker.py:26`
- 问题：`finished = pyqtSignal(bool, str)` 覆盖了 QThread 自带的**无参** `finished` 信号（`run()` 结束时由 C++ 发出）。这是 Qt 官方明确警告的反模式。
- 影响：任何对内置 `finished` 的隐式依赖（如 `worker.finished.connect(thread_cleanup)`、`deleteLater` 惯用法）会连到 Python 信号而非 C++ 信号，线程收尾逻辑静默失效；未来引入 QThread 生命周期管理时必踩坑。
- 修复：重命名为 `result = pyqtSignal(bool, str)`，全项目同步替换。

**修复方案（2026-10-18 已实施）：** `common/base_worker.py` 中 `finished = pyqtSignal(bool, str)` 重命名为 `result = pyqtSignal(bool, str)`，恢复 QThread 内置无参 `finished` 信号的原生语义。全项目同步替换：8 个插件 Worker 的 `self.finished.emit(...)` → `self.result.emit(...)`、UI 侧 `worker.finished.connect(...)` → `worker.result.connect(...)`，以及全部相关测试（`test/test_base_worker.py` 断言更新为验证 `result` 信号且不遮蔽内置 `finished`；其余 `test_p3_*` 等测试的连接同步改名）。`toolbox.py` 中 `sidebar_anim.finished` 等属于 QPropertyAnimation 内置信号，未受影响。

### H6. 图片拼接：画布像素总量无上限，峰值内存可达数十 GB ✅

- 位置：`plugins/image_stitcher.py:288`、`:337`
- 问题：尺寸校验只限单边（`batch_w/batch_h ≤ 60000`），允许 60000×60000 RGBA 画布 = 14.4 GB；JPG 输出时 `canvas.split()[3]` 再生成 4 份单通道副本（+14.4 GB）。
- 影响：大图多张拼接时直接 `MemoryError` 或系统假死，外层 `except` 只报"stitch_failed"，用户不知原因。
- 修复：增加 `batch_w * batch_h` 像素预算检查（如 ≤ 200M px）提前报错；`:337` 改用 `canvas.getchannel('A')`（1 份副本替代 4 份）。

**修复方案（2026-10-18 已实施）：** 新增 `MAX_PIXEL_BUDGET = 200_000_000` 常量，在原单边 60000 限制后追加批次级检查，`batch_w * batch_h` 超预算时 `result.emit(False, ...)` 报错返回，错误文案含批次号、尺寸、预算值；JPG/BMP 保存前 `canvas.split()[3]`（4 份单通道副本）改为 `canvas.getchannel("A")`（1 份），峰值内存从约 5 份画布降到约 2 份。i18n 新增 `plugin.image_stitcher.error.pixel_budget_exceeded`。同时该文件 243-259 行 `open(out_path,'ab')` 探测（H4 同源问题）改为复用已修复的 `common/utils.check_file_writable`。

### H7. 扫描 / 删除期间可重入，旧 Worker 被覆盖导致崩溃 ✅

- 位置：`plugins/file_deduplicator.py:491-516`、`plugins/empty_folder_cleaner.py:558-587`、`:699-711`
- 问题：扫描期间"浏览"按钮与拖拽输入框未禁用，`start_scan` 无运行中守卫。`self.worker` 被重新赋值后旧 QThread 的 Python 对象失去引用，可能被 GC 触发 `QThread: Destroyed while thread is still running` 硬崩溃，且两套信号交叉写入同一 UI。
- 影响：进程崩溃。
- 修复：`start_scan` 开头检查 `self.worker and self.worker.isRunning()`，是则拒绝；扫描期间禁用 browse 与拖拽。

**修复方案（2026-10-18）：**

- **`empty_folder_cleaner.py` 已完成**：新增 `_busy()` 辅助（检查 `self.worker.isRunning()`）；`start_scan` 与 `delete_selected` 开头加防重入守卫，命中则 `show_warning` 提示"正在扫描或删除中"并 return（新增 i18n key：`plugin.empty_folder_cleaner.warning.busy`）；扫描/删除期间禁用 `browse_btn`、`folder_display`，完成回调（`scan_finished`/`delete_finished`）恢复。
- **`file_deduplicator.py` 已完成**：新增 `_is_busy()` 与 `_set_inputs_enabled()`；`start_scan`/`delete_duplicates` 开头加 `_is_busy()` 守卫，运行中则拒绝并弹窗提示（新增 i18n key：`plugin.file_deduplicator.warning.scanning_in_progress`）；扫描/删除期间禁用 `browse_btn` 与 `folder_display`，完成回调恢复。

### H8. 图片压缩 / 格式转换：单个坏文件中止整批 ✅

- 位置：`plugins/image_compressor.py:132-135`、`plugins/image_format_converter.py:99-102`
- 问题：某文件损坏或被占用抛异常即跳出整个循环，已处理进度白费，只报最后一个错误。`image_scaler.py:117` 是 per-file 捕获，三个插件行为不一致。
- 影响：批量处理体验差；错误信息不完整。
- 修复：参照 scaler 改为 per-file try，统计成功 / 失败数，失败文件列入最终消息。

**修复方案（2026-10-18 已实施）：** compressor 与 converter 的 Worker.run() 改为 per-file 循环：每文件独立 try（`_compress_one`/`_convert_one`），成功计数、失败累计进 `failed_files`，progress 每文件照常推进；结果经 `_emit_result` 汇总——全部成功用原键，有失败时用新增 `msg.compress_summary`/`msg.convert_summary`（"成功 X 张，失败 Y 张"）+ 失败文件明细（复用 failures_header/more_failures 格式）。`image_scaler.py` 原已是 per-file 范本，同步补上失败文件明细进 result 消息（原先仅 print 到 stdout）。三插件行为现已一致。

### H9. 图片插件 save 不传 EXIF / ICC，元数据整体丢失 ✅

- 位置：`plugins/image_compressor.py`、`image_format_converter.py`、`image_scaler.py` 的 save 调用；`common/utils.py:36-46`（`load_oriented_image`）
- 问题：`load_oriented_image` 已烘焙方向，但 save 不带 `exif=img.info.get('exif')`，相机型号 / GPS / 拍摄时间被清空；`image_format_converter.py:79-80` 主动删 ICC 以绕过"broken data stream"，导致广色域图偏色。
- 影响：元数据丢失；广色域图片偏色。同类问题见 `image_to_pdf.py:176-177`、`:185-192`。
- 修复：save 传 `exif`；ICC 丢失应通过完整读取源流解决，而非删除。

**修复方案（2026-10-18 已实施）：**

- **compressor / converter / scaler**：在 `load_oriented_image` 打开源图后捕获 `exif = img.info.get('exif')`，save 时传入 `exif=exif`（converter 仅对支持 EXIF 的 JPEG/PNG/WEBP/TIFF 传入）。相机型号 / GPS / 拍摄时间不再丢失。
- **converter ICC**：仍保留既有降级（删除 ICC）但加注释说明无损保留超出本次范围，未扩大改动面。
- **image_to_pdf.py**：定位 `176-177` 处 `del img.info['icc_profile']` 实为误诊——删除保存侧 ICC 对"broken data stream"无效却导致广色域偏色。改为：`_load_oriented_image` 仅当源模式为 RGB 类时保留 ICC（避免 CMYK/L 转 RGB 后 ICC 与像素不符错标）；`_prepare_image` 在生成新画布的路径末尾把 ICC 回填；批量保存改为读取 `img.info.get('icc_profile')` 并显式写入 `save_options['icc_profile']`，让 ICC 随 img2pdf/PIL 后端进 PDF。

### H10. PNG 压缩级别映射错误，quality=100 时反而不压缩 ✅

- 位置：`plugins/image_compressor.py:122`
- 问题：`compress_level = 10 - quality/10`，quality=100 时 compress_level=0（zlib 零压缩），"压缩"出的 PNG 反而比原图大；quality 滑杆语义对 PNG 失效。
- 影响：PNG 压缩功能名存实亡。
- 修复：PNG 为无损格式，固定 `compress_level`（如 9）或将取值 clamp 到 6–9，并去除滑杆对 PNG 的影响。

**修复方案（2026-10-18 已实施）：** PNG 分支固定 `compress_level = 9` + `optimize=True`（PNG 无损，quality 滑杆对其无意义），杜绝 quality=100 时 zlib 零压缩导致"越压越大"；JPEG/WEBP 分支保持 `quality` + `optimize` 不变。

### H11. PDF 插件未检查加密状态 ✅

- 修复：打开后检查 `needs_pass`，需密码时明确报错。

**修复方案（2026-10-18 已实施）：** 两个插件在 `fitz.open(...)` 之后新增加密检查——`pdf_merger.py`（PDFMergeWorker.run 循环内）：`doc.is_encrypted and doc.needs_pass` 命中时关闭 doc 与 merged 文档，emit 含文件路径的明确错误后 return，不再静默产出 0 页"合并成功"；`pdf_splitter.py`（PDFSplitWorker.run）打开后同样检查并提前报错退出。i18n 新增 `plugin.pdf_merger.error.encrypted` / `plugin.pdf_splitter.error.encrypted`（按"先 zh_CN.json、再 en.json、后代码 t() 引用"顺序），`scripts/check_i18n.py` 校验通过。

### M2. `load_oriented_image` 峰值内存约 3× 图像 ✅

- 位置：`common/utils.py:36-46`
