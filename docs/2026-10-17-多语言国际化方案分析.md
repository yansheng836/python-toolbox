# 多语言（国际化）方案分析

> 分析日期：2026-10-17
> 状态：需求已确认，方案分析完成，尚未进入实现
> 适用版本：v2.0.6 及后续版本
> 当前语言范围：简体中文、英文；架构预留后续语言扩展能力

## 1. 需求记录

### 1.1 功能需求

- 当前版本支持两种语言：简体中文（`zh_CN`）、英文（`en`）。
- 架构需要预留语言扩展能力，后续可新增繁体中文（`zh_TW`）或其他语言，不需要改动核心刷新逻辑。
- 用户可以在设置页切换语言，不需要重新安装应用。
- 国际化范围覆盖**所有用户可见文本**，包括：
  - 主窗口标题、侧边栏、首页、菜单栏、托盘菜单。
  - 设置页的标题、说明、按钮、版本信息、链接文字。
  - 各插件的标题、描述、卡片标题、表单标签、按钮、下拉选项、占位提示。
  - 文件列表的表头、操作按钮、水印提示。
  - 任务进度、状态文本、成功/错误/警告弹窗。
  - 工作线程生成的处理中消息、完成消息和错误消息。
- 语言切换后**优先立即刷新当前界面**；如果某些场景无法立即刷新，则提示用户重启应用后生效。
- 语言选择需要持久化，重启应用后保持上次选择。

### 1.2 非功能需求

- 保持单 exe 分发方式，不引入体积过大的运行时依赖。
- 尽量复用现有 `ToolPlugin`、`Theme`、`update_theme()` 等架构模式。
- 配置不写入 `C:\` 根目录，避免管理员权限、UAC 和杀毒软件问题。
- 各语言翻译文件的 key 必须一致，避免运行时出现回退到 key 的情况；新增语言时通过完整性校验阻止缺 key 发布。
- 英文界面下不能出现明显的文字截断或布局错乱。

### 1.3 范围边界

纳入范围：

- `config.py`
- `toolbox.py`
- `common/` 下的公共组件和工具函数
- `plugins/` 下的 8 个插件
- `main.py` 的启动流程

暂不纳入：

- `menu_system.py`：当前应用未导入的遗留示例。
- `test/toolbox2.py`：测试用备份实现。
- `settings_page.py`：当前应用未使用的重复设置页，建议在实施前合并或删除。
- 第三方库返回的原始异常文本（如 Pillow、PyMuPDF 的错误信息）。处理方式是保留原文，并在外层增加本地化上下文，例如“压缩失败：<原始错误>”。

## 2. 现有架构盘点

### 2.1 代码结构

应用是 PyQt6 桌面程序，主要结构如下：

- `main.py`：创建 `QApplication` 和 `ToolboxWindow`。
- `toolbox.py`：主窗口、`ToolPlugin` 基类、`Theme`、`Card`、`SelectableLabel`、`AnimatedButton`、`SidebarButton`、`WelcomePage`、内置 `SettingsPlugin`。
- `config.py`：应用信息、`PLUGIN_MODULES`、`FEATURE_MODULES`、`WELCOME_CONFIG`、UI 和字体配置。
- `common/`：`FileListPanel`、`ActionPanel`、`BaseWorker`、消息框、对话框和工具函数。
- `plugins/`：8 个通过 `importlib` 动态加载的插件。

### 2.2 文本分布

文本目前分散在以下位置：

| 位置 | 典型文本 | 说明 |
|---|---|---|
| `config.py` | 应用名、插件名、插件描述、欢迎页文案 | 模块导入时求值，语言切换后不会自动变化 |
| `toolbox.py` | 侧边栏、菜单、托盘、欢迎页、设置页 | 手写控件，需要逐个刷新 |
| `common/` | 表头、按钮、水印、文件对话框标题 | 被多个插件复用 |
| `plugins/` | 插件标题、表单标签、下拉项、状态消息 | 8 个插件，文本量最大 |
| worker 的 `run()` | “正在处理”“成功压缩 N 张图片”等 | 在工作线程中生成，需要可翻译的消息 key |

粗略统计：`setText`、`addItem`、`Card(title=...)`、`QLabel/SelectableLabel` 等调用约 300 处，加上 worker 消息和动态拼接文本，预计需要整理 **400–600 条**可翻译文本。

### 2.3 可复用的现有机制

主题切换已经形成了成熟的传播链路：

1. `SettingsPlugin.set_theme()` 调用 `ToolboxWindow.apply_theme()`。
2. `ToolboxWindow.apply_theme()` 遍历所有插件，调用 `plugin.update_theme(theme)`。
3. 每个插件更新自己的控件样式。

语言切换可以复用同样的模式：

1. 设置页调用 `i18n.set_language(code)`。
2. `LanguageManager` 发出 `language_changed` 信号。
3. `ToolboxWindow.retranslate_ui()` 更新主框架，再遍历插件调用 `plugin.retranslate_ui()`。

## 4. 候选方案

### 4.1 方案 A：Qt 原生国际化（`QTranslator` + `.ts/.qm`）

做法：

- 使用 `self.tr("...")` 或 `QCoreApplication.translate("Context", "...")` 包裹文本。
- 使用 `pylupdate6` 扫描 Python 文件生成 `.ts`。
- 使用 Qt Linguist 翻译，使用 `lrelease` 编译 `.qm`。
- 运行时通过 `QTranslator` 加载 `.qm` 并 `installTranslator()`。

优点：

- Qt 官方标准方案，复数（`%n`）、上下文、消歧义支持完善。
- Qt Linguist 适合多人协作和翻译审校。
- Qt 标准控件和对话框可以直接复用 `qtbase_*.qm`。

缺点：

- 项目没有 `.ui` 文件，Qt Designer 自动生成的 `retranslateUi()` 用不上，仍要手写刷新逻辑。
- 当前环境只有 `pylupdate6`，没有 `lrelease`，需要额外安装 Qt SDK 或 PySide6 才能编译 `.qm`。
- `config.py` 中的模块级常量必须在运行时求值，改造量不小。
- 所有字符串仍需要手工包裹为 `tr()`，并不能自动完成国际化。

### 4.2 方案 B：JSON 词典 + 自建 LanguageManager

做法：

- 使用 `i18n/zh_CN.json`、`i18n/en.json` 保存当前翻译；新增语言只需增加 `i18n/<locale>.json`，不需要改代码。
- 代码中使用语义化 key，例如 `t("button.start_compress")`。
- `LanguageManager` 负责当前语言、加载词典、发出 `language_changed` 信号。
- 主窗口和插件实现 `retranslate_ui()`，在信号触发时刷新文本。

优点：

- 无新增运行时依赖。
- 翻译文件是纯文本，便于审查、diff 和自动生成。
- 即时切换逻辑完全可控，适合当前手写 UI。
- 配置和资源打包简单，适合 PyInstaller 单 exe。

缺点：

- 没有自动抽取工具，需要额外编写 key 覆盖校验脚本。
- 复数处理需要自己实现简单规则。
- 没有 Qt Linguist 的可视化翻译流程。

### 4.3 方案 C：gettext + Babel（`.po/.mo`）

做法：

- 使用 `_()`、`ngettext()`、`pgettext()` 包裹文本。
- 使用 Babel 或 xgettext 提取 `.po`，使用 Poedit 翻译，编译为 `.mo`。
- 运行时加载 `gettext.translation()` 对象。

优点：

- Python 生态标准方案，成熟稳定。
- 复数、上下文支持较好，翻译工具丰富。

缺点：

- 需要 Babel 或 msgfmt 工具链。
- `.mo` 是二进制文件，打包和审查不如 JSON 直观。
- 中文原文作为 `msgid`，修改原文会导致翻译失效。
- Qt 标准对话框仍需单独加载 `qtbase_*.qm`。

### 4.4 方案 D：Fluent（`fluent.runtime`）

做法：

- 使用 `.ftl` 文件描述消息，支持复数、性别、变量等自然语言规则。

优点：

- 表达能力强，适合复杂自然语言场景。

缺点：

- Python 桌面应用中使用较少，工具链和团队熟悉度低。
- 对本项目当前 2 种语言、以短文本为主的场景属于过度设计。

### 4.5 方案 E：轻量第三方库（如 `python-i18n`）

做法：

- 使用第三方库提供的 `t()` 和 YAML/JSON 词典。

优点：

- 起步快，API 简单。

缺点：

- 多一个运行时依赖。
- 控件刷新、复数、key 校验仍需要自己处理，长期控制力不如自建方案。

## 5. 方案对比

| 维度 | A Qt 原生 | B JSON 自建 | C gettext+Babel | D Fluent | E 轻量库 |
|---|---|---|---|---|---|
| 运行时即时切换 | 可行，需手动刷新 | 可行，信号驱动 | 可行，需切换翻译对象 | 可行 | 可行 |
| 现有代码改造量 | 高 | 中高 | 中高 | 高 | 中高 |
| 工具链/依赖 | 需补 `lrelease` | 无 | Babel/msgfmt | fluent.runtime | python-i18n |
| 文本抽取 | `pylupdate6` 自动 | 自写校验脚本 | Babel/xgettext | 一般 | 无 |
| 复数/上下文 | 强 | 简单实现即可 | 强 | 最强 | 弱 |
| Qt 标准对话框 | 可加载 `qtbase` | 需额外加载 `qtbase` | 同 B | 同 B | 同 B |
| PyInstaller 打包 | 打包 `.qm` | 打包 JSON | 打包 `.mo` | 打包 `.ftl` | 打包数据文件 |
| 翻译协作 | Qt Linguist 最佳 | JSON 通用 | Poedit 最佳 | 一般 | 一般 |
| 适合本项目 | 中 | 高 | 中 | 低 | 中 |

## 6. 推荐方案

### 6.1 结论

推荐 **方案 B：JSON 词典 + LanguageManager + `t()` + `retranslate_ui()`**，并额外加载 Qt 自带的 `qtbase_*.qm`，仅用于标准按钮和文件对话框。

选择理由：

1. 当前 UI 全部是手写 PyQt6 代码，没有 `.ui` 文件，Qt 原生方案的主要优势无法发挥。
2. 当前环境缺少 `lrelease`，Qt 原生方案需要额外工具链，不符合单 exe、低依赖目标。
3. 项目当前只有 2 种语言、约 400–600 条文本，JSON 方案足够且更易维护；新增语言只需增加一个 JSON 文件并注册语言代码。
4. PyQt6 已自带 `qtbase_zh_CN.qm`、`qtbase_zh_TW.qm`、`qtbase_en.qm`，标准对话框可以直接复用。
5. 即时切换的关键是刷新链路，而不是翻译文件格式；方案 B 的信号驱动方式更直接。

### 6.2 目录与职责

```text
common/i18n.py           # LanguageManager、t()、语言加载、复数处理
common/app_settings.py   # 配置文件读写、默认值、迁移
i18n/zh_CN.json          # 简体中文（源语言）
i18n/en.json             # English
# 后续扩展语言时新增 i18n/<locale>.json
scripts/check_i18n.py    # 校验 key 覆盖、占位符一致性
```

`t()` 的行为约定：

- 当前语言找不到 key 时，回退到 `zh_CN`；仍找不到则返回 key 本身，便于发现遗漏。
- 支持命名占位符，例如 `t("msg.compress_done", count=5)`。
- 复数消息可以写成 `{"one": "...", "other": "..."}`，根据 `count` 选择；中文的 `one` 和 `other` 可以使用相同文本。
- `t()` 只做字典查找和字符串格式化，不依赖 Qt 控件，可在工作线程中安全调用。

### 6.3 即时刷新流程

```text
设置页选择语言
  -> AppSettings 立即写入 config.ini
  -> i18n.set_language(code)
       -> 重新加载/安装 qtbase QTranslator（仅标准对话框）
       -> 发出 language_changed 信号
          -> ToolboxWindow.retranslate_ui()
               -> 窗口标题、侧边栏、首页、菜单、托盘
               -> 每个 plugin.retranslate_ui()
```

实现要点：

- `ToolPlugin` 增加默认空实现的 `retranslate_ui()`，与现有 `update_theme()` 对称。
- `ToolboxWindow` 连接 `i18n.language_changed`，统一遍历插件。
- 各插件保存需要更新的控件引用，或使用统一绑定器：

```python
i18n.bind(self.title_label, "setText", "plugin.image_compressor.name")
i18n.bind(self.browse_btn, "setText", "button.browse")
i18n.bind(self.output_path, "setPlaceholderText", "placeholder.output_dir")
i18n.bind_combo(self.format_combo, [
    ("fmt.keep", "keep"),
    ("fmt.jpg", "JPG"),
    ("fmt.png", "PNG"),
])
```

- 绑定器在控件 `destroyed` 时自动解绑，避免悬空引用。
- 组合型内容（去重结果树、欢迎页功能卡片）使用显式 `retranslate_ui()` 重新渲染。

运行时行为：

- 正在运行的任务不重启。worker 每次发消息时调用 `t()`，切换语言后新产生的状态文本使用新语言。
- 已经显示在界面上的旧文本保持到下一次刷新，这是可接受的边界行为。
- 已打开的模式对话框不会即时刷新，关闭后重新打开即可；如果要求严格，可以在模式对话框存在时禁用语言切换。

### 6.5 工作线程与动态消息

worker 消息改为在发消息时调用 `t()`，例如：

```python
from common.i18n import t

self.status.emit(t("worker.processing", name=os.path.basename(file_path)))
self.finished.emit(True, t("msg.compress_done", count=processed))
self.finished.emit(False, t("error.compress_failed", error=str(e)))
```

约定：

- 用户数据（文件路径、文件名、外部库错误原文）不翻译，只通过参数传入。
- 计数类消息使用 `count` 参数，由 `t()` 处理单复数。
- 工作线程只调用 `t()`，不直接操作 Qt 控件。

### 6.6 Qt 标准对话框

使用单独的 `QTranslator` 加载 Qt 自带翻译：

```python
translator = QTranslator()
translator.load("qtbase_zh_CN", translations_dir)
app.installTranslator(translator)
```

说明：

- 该翻译器只负责 `QMessageBox` 的 OK/Cancel/Yes/No、`QFileDialog` 的标准标签等 Qt 内置文本。
- 应用自身的文本继续使用 `t()`，两者互不冲突。
- 切换语言时需要先移除旧翻译器，再安装新翻译器。
- 英文可以使用 `qtbase_en.qm`，也可以移除翻译器使用 Qt 默认英文。

### 6.7 复数与占位符

JSON 示例：

```json
{
  "msg.compress_done": {
    "one": "Compressed {count} image",
    "other": "Compressed {count} images"
  },
  "worker.processing": "Processing: {name}"
}
```

约定：

- 占位符统一使用命名参数，不使用位置参数，避免不同语言语序不同导致错误。
- 各语言的占位符集合必须一致，由 `scripts/check_i18n.py` 校验；新增语言时同样纳入校验。
- 翻译文本中如果需要字面量花括号，使用 `{{` 和 `}}` 转义。

### 6.8 语言扩展与术语表

当前版本只交付简体中文和英文。后续新增繁体中文或其他语言时，需要统一术语，避免同一概念出现多种译法。下面保留一份术语参考（繁体中文为未来扩展示例，不属于当前交付范围）：

| 简体 | 未来扩展（繁体示例） | 英文 |
|---|---|---|
| 文件 | 檔案 | File |
| 文件夹 | 資料夾 | Folder |
| 设置 | 設定 | Settings |
| 图片 | 圖片 | Image |
| 质量 | 品質 | Quality |
| 默认 | 預設 | Default |
| 保存 | 儲存 | Save |
| 加载 | 載入 | Load |
| 打印 | 列印 | Print |
| 复制 | 複製 | Copy |

后续新增一种语言的步骤：

1. 新增 `i18n/<locale>.json`，补齐全部 key 和占位符。
2. 在 `i18n` 的语言注册表中增加语言代码和显示名称（如 `zh_TW` / `繁體中文`）。
3. 如果 Qt 提供了对应的 `qtbase_<locale>.qm`，同步加入打包资源；没有则标准对话框回退英文。
4. 运行 `scripts/check_i18n.py`，确认 key、占位符与源语言一致。
5. 在设置页语言下拉框中确认新语言可见，并补充对应 UI 测试。

核心刷新逻辑（`LanguageManager`、`retranslate_ui()`、绑定器）不随语言数量变化。

## 7. 配置文件设计

### 7.1 存放位置

不建议写入 `C:\` 根目录，原因包括：

- 需要管理员权限，普通用户运行时可能失败。
- 容易被 UAC、杀毒软件或系统策略拦截。
- 多用户环境下会互相覆盖。
- 应用安装在 `Program Files` 时，exe 所在目录通常不可写。

推荐使用 Qt 标准路径：

```python
app.setOrganizationName("yansheng836")
app.setApplicationName("Toolbox")
config_dir = QStandardPaths.writableLocation(
    QStandardPaths.StandardLocation.AppConfigLocation
)
config_path = os.path.join(config_dir, "config.ini")
```

本机实测路径为：

```text
C:/Users/Administrator/AppData/Local/yansheng836/Toolbox/config.ini
```

### 7.2 配置格式

使用 INI 格式，便于用户查看、备份和迁移：

```ini
[general]
language=zh_CN
theme=dark

[window]
geometry=...
state=...

[meta]
config_version=1
```

### 7.3 启动与迁移

启动顺序：

1. 创建 `QApplication`。
2. 设置 `organizationName` 和 `applicationName`。
3. 创建 `AppSettings`，读取配置文件。
4. 根据 `general/language` 初始化 `i18n`。
5. 创建 `ToolboxWindow`。

迁移规则：

- 首次创建 INI 时，读取旧的 `QSettings("Toolbox", "App")` 注册表值，复制 `theme`、`geometry`、`windowState`。
- 增加 `config_version`，后续结构变化时执行迁移函数。
- 配置文件缺失或损坏时使用默认值，并记录错误信息。
- 写入前备份为 `config.ini.bak`。
- 启动时不能像当前 `init_theme()` 那样无条件覆盖已保存值。

### 7.4 绿色版配置

如果需要单 exe 携带配置，可以支持便携模式：

- exe 同目录存在 `portable.flag`，且目录可写时，使用 `exe_dir/config.ini`。
- 否则回退到 `AppData/Local/yansheng836/Toolbox/config.ini`。

这样既支持 U 盘携带，也能兼容安装在只读目录的场景。

### 7.5 当前配置实现的问题

当前使用：

```python
QSettings("Toolbox", "App")
```

在 Windows 上实际写入注册表：

```text
HKEY_CURRENT_USER\Software\Toolbox\App
```

注册表配置重启后不会丢失，但不透明、不可携带、不便于备份。建议迁移到 INI 文件。

另外，`toolbox.py:1310-1313` 的 `init_theme()` 启动时强制设置 `dark` 并覆盖保存值，导致主题设置实际上没有恢复。实施语言持久化时不能复制该逻辑。

## 结论

本项目当前交付简体中文和英文，适合采用 **JSON 词典 + LanguageManager + `retranslate_ui()` + Qt `qtbase` 标准翻译** 的方案，并预留后续语言扩展能力。真正的工作重点是先完成“显示文本与业务稳定值/插件 ID 解耦”，再补齐逐控件刷新和配置持久化。方案确定后，建议先做 P0–P1 的基础设施，再按插件逐步迁移，避免一次性大改导致回归。
