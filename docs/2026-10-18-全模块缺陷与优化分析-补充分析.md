## 一、总体结论

前一份文档整体修复质量高：数据安全（junction 越界、静默覆盖、回收站）、崩溃（Worker 重入/遮蔽）、旧死代码清理等主链路问题已解决。**但"取消机制统一"和"失败聚合统一"这两项重构覆盖不完整，留下删除类插件与个别转换插件的盲区**，具体表现为四类：

1. **"取消"按钮名存实亡**：`BaseWorker`/`ActionPanel` 已内建取消约定，但**所有删除类插件**（`empty_folder_cleaner`、`file_deduplicator`）的 Worker 不响应 `is_cancelled()`，`ActionPanel.cancelled` 信号也未连接——界面上出现了"取消"按钮，点了毫无反应。
2. **取消被当作出错弹出**：多数转换插件 `result.emit(False, task_cancelled)` 后统一走 `show_error`，用户主动取消却看到"错误"对话框。
3. **失败聚合遗漏边缘路径**：`image_to_pdf` 的批内失败/合并失败不计入 `skipped`，甚至整批全失败时用"空临时 PDF 触发全局 abort"。
4. **"统一"未覆盖一致的进度语义**：`image_scaler` 的进度条最大值与实际喂入值维度不一致，进度显示失真。

另发现一处**前份文档宣称"已修复"项仍残留**的真缺陷（`app_settings._check_version` 节名引用错误），详见 B1。

## 二、高严重度问题（数据/流程/功能）

### H-A. 所有删除类插件"取消"按钮名存实亡（扫描/删除均无法取消） ✅

- 位置：`plugins/empty_folder_cleaner.py`（`EmptyFolderWorker._run_scan`/`_run_delete`、`scan_panel`/`delete_panel` 信号）`plugins/file_deduplicator.py:433-449, 558-566, 760-767, 1164-1173`
- 问题：
  - `ActionPanel.start_task()` 会在任务运行中把按钮文案切换为"取消"且可点（`action_panel.py:131-132`），点击发 `cancelled` 信号。但**两个删除类插件都没有把 `*.cancelled` connect 到 `worker.cancel`**——
    - `empty_folder_cleaner.py`: `scan_panel.cancelled`/`delete_panel.cancelled` 从未 connect；`EmptyFolderWorker.run` 全程无 `is_cancelled()` 检查点。用户点"取消"零响应，大目录扫描/删除只能等自然结束。
    - `file_deduplicator.py`: 扫描有个旁置的 `cancel_scan_btn`（443/773）真正生效，但 `scan_panel.cancelled` 也未连接——扫描期间**两个"取消"并排，面板那个是死按钮**；删除阶段 `delete_panel.cancelled` 未连接又无旁置按钮 → **删除彻底无法取消**。
  - 与文档 L 项"7 个转换类插件 Worker 已加取消检查并连 cancelled"直接对比：**删除类插件被排除在这 7 个之外，是统一重构的盲区**。
- 影响：删除大量文件/扫描大目录时用户无法中断；更糟的是 `delete_panel` 显示"取消"却无效，用户以为已取消，实际删除仍在后台进行，可能误删到一半。

**已实施修复方案（2026-10-19）：**

- **`empty_folder_cleaner.py`**（此前扫描/删除均完全无法取消）：
  - 新增模块级 `_ScanCancelled` 异常。
  - `_scan_directory()` / `find_empty_folder_candidates()` 增加可选参数 `cancelled`（可调用对象），在每次递归入口检查，返回真值即抛 `_ScanCancelled`——使深度递归扫描可中断。
  - `EmptyFolderWorker._run_scan` 注入 `self.is_cancelled`，捕获 `_ScanCancelled` 后 `result.emit(False, task_cancelled)` 返回，不再上报虚假候选。
  - `_run_delete` 循环内在每个目录删除前检查 `is_cancelled()`，取消时上报已删除/失败进度后 `result.emit(False, task_cancelled)` 返回。
  - `start_scan` / `delete_selected` 连接 `scan_panel.cancelled` / `delete_panel.cancelled` → `worker.cancel`。
- **`file_deduplicator.py`**（worker 已有取消标志，缺的是接线）：
  - `start_scan` 连接 `scan_panel.cancelled` → `worker.cancel`（扫描可取消，不再依赖旁置死按钮）。
  - `delete_duplicates` 连接 `delete_panel.cancelled` → `worker.cancel`（删除从"无法取消"变为可取消）。

**验证：** `py_compile` / `pyflakes` 通过；复用现成 i18n 键 `common.msg.task_cancelled`（zh/en 均有），`check_i18n.py` 通过；两插件 12 个 pytest 用例全部通过。

**注：** 未处理的边界——H-C（`file_deduplicator` 两个 worker 用自定义 `cancel_requested` 绕过 `BaseWorker` 标准约定）本次未统一，工作正常但为防回归项；取消后 `success=False` 仍走现有 `show_error`（M-D"取消当错误弹"为独立条目，不在本次范围）。

### H-B. 去重插件删除完成总弹"信息"对话框（含失败/取消） ✅

- 位置：`plugins/file_deduplicator.py:1185-1194`
- 问题：`delete_finished` 无论 `success` 为何都 `show_info`。当 `success=False`（用户取消、TOCTOU 跳过、send2trash 失败、越界拒绝）时，弹"信息"图标装载失败明细，误导用户对删除结果严重性的判断。对照 `empty_folder_cleaner.py:753-764` 已正确按 success 分流 `show_info`/`show_error`，行为不一致。

**已实施修复方案（2026-10-19）：** `delete_finished` 按 `success` 分流——成功走 `show_info`（标题 `dialog.delete_result`），失败/取消走 `show_error`（标题 `dialog.error_title`，与 `scan_finished` 一致）。`auto_rescan` 等后续逻辑不变。

**验证：** `py_compile` / `pyflakes` 通过；`test_p3_file_deduplicator.py` 7 个用例全部通过。

**注：** 取消消息 `task_cancelled` 现走 `show_error`——与 M-D"取消当错误弹"重叠，本次仅纠正"信息图标装失败"的误导，取消弹窗类型统一属 M-D 范围。

### H-C. `file_deduplicator` 两个 Worker 绕过 `BaseWorker` 标准取消约定

- 位置：`plugins/file_deduplicator.py:120-123, 272-273`（`FileDeduplicationWorker`）、`:290, 376-377`（`FileDeletionWorker`）
- 问题：`BaseWorker` 内建 `_cancelled`/`is_cancelled()`/`cancel()`，文档 L 项宣称"BaseWorker 内建取消机制，7 个转换类插件已统一"。但这两个去重 Worker 各自自定义 `cancel_requested` 并**覆盖基类 `cancel()`**，循环里检查 `self.cancel_requested` 而非 `is_cancelled()`。当前能工作只是因为 `cancel()` 同时设了 `cancel_requested`；一旦后续有人按标准模式在 run 中加 `is_cancelled()` 检查点并连 `cancelled→cancel`，将**完全不生效**（基类 `_cancelled` 恒 False）。`empty_folder_cleaner` 则相反——用了基类但没接信号、也没在 run 里检查。
- 修复方案：删除自定义标志，统一 `cancel()` + `is_cancelled()`。
- 置信度：已读源码确认（属一致性/防回归缺陷，非当前崩溃）。

### H-D. `image_to_pdf`：某批图片全部打开失败 → 空临时 PDF → 整个任务 abort，且批内/合并失败不计入 skipped

- 位置：`plugins/image_to_pdf.py:241-244, 274-279, 315-317`
- 问题一（高）：FITZ 可用时，批内 `fitz.open(jpg_file)` 单张失败即 `continue`（241-243），若某批（≤50 张）全部失败，`doc` 仍被 `save(temp_pdf)` 成空 PDF → 275 行 `getsize==0` → `raise` → 349 行 catch → `result.emit(False, convert_failed)`，**整个任务中止，之前已成功生成的批次全部作废**。PIL 后端 `pil_imgs` 为空时同样留空文件触发此路径。这与文档 H8"per-file 失败聚合"精神相悖——本插件未纳入 H8 的 per-file 聚合改造。
- 问题二（中）：`image_to_pdf.py:241` 批内 JPEG 失败、`:315` 合并临时 PDF 失败均 `continue` **不递增 `skipped`**，而 `:155/:185` 又递增 `skipped`——同一成功消息里失败渠道统计不一致，被丢弃的页不被报告。
- 修复方案：批内全失败应视为"该批跳过"并计入 skipped/失败清单，而不是产生空 PDF 触发全局 abort；两条 `continue` 补 `skipped += 1`。
- 置信度：问题一确认，触发条件为"某批图片全损坏"（较苛刻，故定为高-中边界）；问题二确认。

## 三、中严重度问题（体验/性能/语义）

### M-A. `image_scaler` 进度条最大值与进度值维度不一致，进度显示失真

- 位置：`plugins/image_scaler.py:124-125, 395-397, 402-407`
- 问题：`ScalingWorker` 用自定义 `progress_updated.emit(int((i+1)/total*100), i+1)` 发出 **0-100 百分比**；但 `start_scaling` 调 `self.action_panel.start_task(len(files), ...)` 把进度条 `maximum` 设为**文件数**，`on_progress_updated` 又把百分比喂给 `update_progress(progress)`。输入 5 张图时，首张即 `update_progress(20)` 对 max=5 → 进度条立刻到 100% 满。其余插件（compressor/converter/pdf）走 `BaseWorker.progress` 发 `i+1` 且 `start_task(len(files))`，语义一致；此处是唯一不一致点。
- 修复方案：改用 `BaseWorker.progress` 发 `i+1`，或把 `start_task` 的 maximum 设为 100。
- 置信度：已读源码确认。

### M-B. PDF 合并/拆分：异常路径 `fitz` 文档对象未关闭（句柄泄漏）

- 位置：`plugins/pdf_merger.py:55, 65, 73, 81-83`；`plugins/pdf_splitter.py:69-75, 99-102, 140-142`
- 问题：`merged = fitz.open()` / `doc = fitz.open(...)` 后，若 `fitz.open(file)`、`insert_pdf`、`save` 抛非加密异常（如损坏 PDF 的 `RuntimeError`），外层 `except Exception` 只 emit 消息就 return，`merged`/`doc`/`new_doc` **均未 close**。PyMuPDF 文档对象虽能靠 GC 最终释放，但依赖不保证时机的引用计数，违反项目"用上下文管理器释放资源"规范（Performance Optimization 章），在长循环/批量场景下可能累积句柄。
- 修复方案：用 `with fitz.open(...) as doc:` 或 `try-finally` 保证关闭。
- 置信度：已读源码确认。

### M-C. PDF 拆分：PDF 路径与图片路径的失败处理不一致，单页损坏会中止整批

- 位置：`plugins/pdf_splitter.py:83-104`（PDF 路径）vs `:110-133`（图片路径）
- 问题：图片路径对锁定输出 `check_file_writable` 失败即 `skipped += 1; continue`（94-98, 123-128）；但 PDF 路径中 `new_doc.insert_pdf`/`new_doc.save` 若抛非锁定异常（如某页损坏）无 per-file try，直接冒泡到 141 外层 catch → 整个任务中止，已成功生成的 `count` 个文件不做成功报告。图片路径对 `_save_pixmap` 的非锁定异常（130 行）也无 per-file 捕获，同样会中止。两路语义不一致，与文档 L 项"M24 每文件保存前 check_file_writable"只覆盖了锁定、未覆盖其它单页失败。
- 修复方案：PDF 路径对 `insert_pdf`/`save` 加 per-file try-except 归入 `skipped`，与图片路径一致。
- 置信度：已读源码确认。

### M-D. 转换类插件取消被当作出错弹出

- 位置：`plugins/pdf_merger.py:220-227`、`plugins/pdf_splitter.py:420-427`、`plugins/file_deduplicator.py:1063-1079`（以及空文件夹扫描 634-653）
- 问题：Worker 在取消时 `result.emit(False, t("common.msg.task_cancelled"))`，UI 的 `*_finished` 收到 `success=False` 统一 `show_error`。用户**主动点取消**却看到红色"错误"对话框，语义错误、惊吓用户。配合 H-A（删除类取消无效）更明显。
- 修复方案：结果消息为"已取消"时走 `show_info` 或不弹窗（仅状态栏提示），或约定取消用独立信号/消息区分。
- 置信度：已读源码确认。

### M-E. `send2trash` 非 OSError 异常逃逸，中止整批删除 ⚠️

- 位置：`plugins/file_deduplicator.py:311-318`（`_delete_one` 仅 `except OSError`）
- 问题：`send2trash` 在网络路径/回收站不可用/跨卷等场景可能抛出非 `OSError` 的异常（如其 `send2trash.exceptions.*`）。此处只捕获 `OSError`，其它异常会冒到 `run()` 的 `except Exception`（369）→ 剩余文件不再处理，`deleted/failed/missing` 统计失真并中止。
- 备注：`send2trash` 的 `TrashPermissionError`/`TrashFullError` 继承自 `OSError` 能捕获；但基类 `Error` 及个别平台异常可能不在 `OSError` 层级。故标 ⚠️，建议实测或以 `except Exception` 兜底归入 failed。
- 修复方案：`_delete_one` 改 `except Exception as exc` 归入 failed，不中止整批；或显式加 `send2trash.exceptions.Error`。
- 置信度：逻辑已读源码确认，异常层级需实测。

## 五、需进一步确认（⚠️）

- **`QApplication.quit` 是否丢失插件设置**（推测）：菜单「退出」(Ctrl+Q)、托盘「退出」走 `QApplication.quit()`，可能**不触发** `ToolboxWindow.closeEvent`（`closeEvent` 是唯一调用 `save_plugins_settings`/`save_geometry` 落盘处）。若成立，这两条退出路径会静默丢失「窗口正常关闭才落盘」的插件设置与窗口几何改动——与文档"正常关闭统一落盘，仅崩溃/强杀丢失"的假设冲突。**需在真实 GUI 环境验证 `quit()` 是否触发 closeEvent**。若确认，应改为让退出路径先 `close()` 或显式调用保存。
